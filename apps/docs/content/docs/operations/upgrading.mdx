---
title: Upgrading
description: Move a live Convoy deployment to a newer version of the code.
---

Convoy deploys from the repository, so upgrading a live instance means
deploying a newer commit — backend, web app, and the CLI workers your team
runs. The order matters when the new version includes schema or data
changes.

## Before you upgrade

- Read the commit range you are about to deploy. Changes to
  `apps/web/convex/migrations.ts` are data migrations, and the deploy runs
  them for you.
- Take a backup if the range includes schema changes — see
  [`Backups and rollback`](/docs/operations/backups-and-rollback).
- Remember the one-way-door rule: schema-**narrowing** deploys are not
  cleanly reversible. Widen-first changes can sit across two releases.

## Standard flow

### 1. Deploy backend and web app

With the [integrated Vercel build](/docs/deployment/deploy-to-vercel),
pushing the new commit to the production branch deploys both: the build
runs `convex deploy` (functions + schema), builds the Next.js app, and starts
any pending data migrations.

If you deploy Convex separately, deploy the backend **first**, then the web
app:

```bash
# from apps/web
CONVEX_DEPLOYMENT="prod:friendly-wolf-872" pnpm convex:deploy
```

`pnpm convex:deploy` pushes the backend and starts pending data migrations.
A plain `npx convex deploy` skips the migrations. They run in the background;
[`Migrations`](/docs/operations/migrations#check-progress) shows how to
check them.

With the [self-hosted Docker setup](/docs/deployment/self-hosting-convex),
run `./self-hosted/upgrade.sh` instead of `git pull`. It deploys each
[upgrade stop](#upgrade-stops) on the way to the latest `main`, and waits
for each one's migrations to finish.

### 2. Update CLI workers

Each machine running `convoy connect` should update its checkout and
restart the bridge:

```bash
git pull
pnpm install
# restart the connect process (supervisor restart, or Ctrl+C and re-run)
```

The CLI talks to the backend through versioned Convex functions; an
outdated worker usually keeps functioning, but keep workers within a
release of the backend to avoid drift. A clean restart re-registers the
session — in-flight threads fail over via the claim lease and are
retryable.

### 3. Verify

- **Settings → Developer** in the web app shows both frontend and backend
  build metadata — confirm both match the deployed commit.
- The web app polls for new frontend versions
  (`NEXT_PUBLIC_APP_VERSION_POLL_INTERVAL_MS`, default 2 minutes), so open
  browser tabs pick up the new build without manual refreshes.
- Run a quick smoke pass from the
  [`Production checklist`](/docs/deployment/production-checklist): sign-in,
  task CRUD, one streamed thread.

## Upgrade stops

Some upgrades remove an old data shape from the schema. Convex refuses to
deploy a schema the stored data doesn't fit, so the migration that converts
the data has to run first, from an earlier commit. A commit you must deploy,
and whose migrations must finish, before going further is tagged
`upgrade-stop-YYYY-MM-DD`.

If you skip one, the deploy fails with a schema validation error and pushes
nothing, along these lines:

```
Schema validation failed.
Document with ID "..." in table "cliSessions" does not match the schema: ...
```

Nothing changed on your deployment. Deploy the stops in order, then the
latest commit.

### Docker installs

```bash
./self-hosted/upgrade.sh
```

It refuses to run over uncommitted changes, then checks out each stop you
don't have yet, runs `start.sh` there, and finishes on the latest `main`.
`start.sh` waits for the data migrations and exits with an error naming any
that failed. The script then stops and leaves the checkout at that stop.
Fix the cause and run it again: it starts from that stop.

### Other installs

List the stops between your deployed commit and `main`, oldest first:

```bash
git fetch --tags
git tag --merged origin/main --no-merged <deployed-commit> --list 'upgrade-stop-*' --sort=version:refname
```

For each one, deploy it the way you normally deploy, then wait until
`lib:getStatus` shows every migration done (see
[`Check progress`](/docs/operations/migrations#check-progress)). Then deploy
`main`. On Vercel, deploy a stop by promoting or redeploying a build of that
tag's commit.

## Rebuild the docs site

If you deploy the docs site and the release touched
`apps/docs/content/`, redeploy it as well — see
[`Deploy the docs site`](/docs/deployment/deploy-docs).

## If the upgrade goes wrong

[`Backups and rollback`](/docs/operations/backups-and-rollback) covers
promoting a previous web deployment and redeploying Convex from a prior
commit — and the schema-migration trap that decides whether rolling back
is safe at all.
