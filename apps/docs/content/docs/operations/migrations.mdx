---
title: Migrations
description: How Convoy runs Convex data migrations on every deploy, and how to run one by hand.
---

Convoy uses Convex for durable application data. Any migration that
changes existing documents should follow a staged deployment flow:
widen the schema, migrate and verify the data, then narrow the schema
in a later deploy.

## Migrations run on every deploy

You don't run migrations yourself. Every deploy pushes the backend and then
calls `migrations:runAll`, which starts whatever that deployment has not run
yet.

| How you deploy | What starts the migrations |
| --- | --- |
| Vercel integrated build | the `vercel-build` script |
| Self-hosted Docker | `./self-hosted/start.sh` |
| By hand | `pnpm convex:deploy` from `apps/web` |
| Local development | `pnpm web:convex:dev`, once each time it starts |

A plain `npx convex deploy` pushes the code and starts nothing. Use
`pnpm convex:deploy` instead. It passes its arguments to `convex deploy` and
picks the deployment from the same environment variables. It refuses
`--env-file`, `--url` and `--admin-key`, so set the target in the
environment.

The deploy fails if the migrations cannot start, or if the first batch
fails. The backend is already pushed by then. Fix the cause and deploy
again.

The migrations component records progress in each deployment. A second call
skips finished migrations and resumes a partial one, so deploying twice is
safe.

## Check progress

Migrations run in the background after the deploy command returns. The
deploy prints the command that shows their state. From `apps/web`:

```bash
npx convex run --prod --component migrations lib:getStatus
```

Drop `--prod` when a deploy key or a self-hosted URL already selects the
deployment. Add `--watch` to follow a long run. Each row has `isDone`, the
number of documents processed, and an `error` if a batch failed.

A failed migration stays failed until something starts it again. Fix the
cause, then deploy again or run it by hand.

## Run a migration by hand

Use these to recover from a failure, or to try a risky migration before it
ships. From `apps/web`:

```bash
# Everything pending
npx convex run --prod migrations:runAll

# One migration
npx convex run --prod migrations:<migrationName>

# Without writing
npx convex run --prod migrations:<migrationName> '{"dryRun": true}'
```

Dry-run one migration at a time. A dry run of `runAll` fails with
`Dry run attempted to update state` when it meets a migration that has
already finished.

## Adding a migration

A migration that changes existing documents ships in two commits.

### 1. The widened commit

The first commit must read both the old and the new data, because the
migration is still running when the new code starts serving requests. It
should:

- keep the old schema shape valid
- write the new shape for new and updated rows
- define the migration and add it to the `runAll` list in
  `apps/web/convex/migrations.ts`
- include a verification query that reports rows still in the old shape
- skip rows that already have the new shape, so a second run changes nothing

Deploying this commit starts the migration.

### 2. Verify, then narrow

Wait for `lib:getStatus` to show the migration done, then run the
verification query:

```bash
npx convex run --prod migrations:<verifyQueryName>
```

Only when it reports no leftovers, ship a second commit that removes the old
schema shape and the code that read it. `convex deploy` refuses a schema the
stored data doesn't fit and pushes nothing, so a narrowing commit fails on
any install that has not finished the migration.

Keep at least one migration in the `runAll` list. An empty list throws, and
every deploy calls it.

## Rollback notes

The widened deploy is usually rollback-friendly because it still
accepts the old data. The narrowed deploy is different: once a schema
removes a legacy field or union value, rolling back code may not be
enough because the data has already changed.

Treat narrowing deploys as fix-forward by default. If rollback might be
needed, take a Convex backup or export before narrowing and read
[`Backups and rollback`](/docs/operations/backups-and-rollback)
before deploying.
