This is the self-hosted path: Convoy's web app and backend run on your own
infrastructure, and your coding agents connect to your instance.

Convoy's backend is Convex, and Convex ships an official self-hosted
build. The repo bundles a Docker Compose setup under `self-hosted/` that
runs the whole stack on one machine:

- **`backend`** — self-hosted Convex (`ghcr.io/convex/convex-backend`);
  database, functions, scheduler, file storage. Client API on port `3210`,
  HTTP actions (`/api/mcp`, `/api/agent/*`) on port `3211`.
- **`dashboard`** — the Convex dashboard (`ghcr.io/convex/convex-dashboard`)
  on port `6791`; data browser, logs, function runner.
- **`web`** — the Convoy Next.js app, built locally from your checkout,
  on port `3000`.

## What still lives in the cloud

Nothing has to. The default auth mode, Convex Auth, keeps accounts in your own
backend. These outside services are optional:

- **Resend.** Sends invitation emails and, in Convex Auth mode, the sign-up
  verification and password reset links. Without it, set
  `AUTH_EMAIL_VERIFICATION=off`: sign-up checks no mailbox and there is no
  password reset. Invitations still work through a copied link. See
  [Email verification](/docs/deployment/auth-and-clerk#email-verification).
- **Google.** "Continue with Google" needs a Google OAuth client.
- **Clerk.** Clerk mode signs people in through Clerk, which has no
  self-hosted offering. A free-tier Clerk app works for a local deployment;
  the login flow needs internet access to `*.clerk.accounts.dev`.

A single pull-and-run image is ruled out by Next.js itself: the
`NEXT_PUBLIC_*` values (Convex URL, auth mode, Clerk publishable key) are baked into
the JavaScript bundle at build time, so the web image must be built per
installation. `docker compose build` handles that.

## Quick start

Prerequisites: Docker with Compose. For Clerk mode, also a Clerk application
set up per [Authentication](/docs/deployment/auth-and-clerk#clerk) (create the
`convex` JWT template).

```bash
./self-hosted/start.sh
```

On the first run the script asks for the auth mode, `convex` (default) or
`clerk`. Choose before the first user signs up; accounts don't move between
modes.

- **convex** asks for an optional Resend API key and `EMAIL_FROM`. With a key
  it sets `AUTH_EMAIL_VERIFICATION=required`, without one `off`. It also sets
  `AUTH_MODE`, `NEXT_PUBLIC_APP_URL` (from `APP_URL`) and the placeholder
  `CLERK_JWT_ISSUER_DOMAIN` on the backend.
- **clerk** asks for your two Clerk API keys and derives the Clerk JWT issuer
  domain from the publishable key.

Then it does the rest: writes `.env`, generates the instance secret and admin
key, starts the backend and dashboard, builds the web image, deploys Convoy's
functions from inside Docker (no Node.js needed on the host), and starts the
web app.
On later runs, review the existing `.env` and back up the data before
upgrading.

## Manual walkthrough

The same steps by hand — useful for understanding the moving pieces or for
customized setups. Requires Node 22+ on the host for the
`npx convex deploy` step.

```bash
cd self-hosted
cp .env.example .env
```

Fill in `.env`: `INSTANCE_SECRET` (`openssl rand -hex 32`) and `AUTH_MODE`
(`convex` or `clerk`). In Clerk mode also `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`
and `CLERK_SECRET_KEY`.

**1. Start the Convex backend and dashboard:**

```bash
docker compose up -d backend dashboard
```

**2. Generate an admin key** (the self-hosted equivalent of a deploy key)
and paste it into `.env` as `CONVEX_SELF_HOSTED_ADMIN_KEY`:

```bash
docker compose exec backend ./generate_admin_key.sh
```

**3. Deploy Convoy's functions and schema.** The standard Convex CLI
targets a self-hosted backend when `CONVEX_SELF_HOSTED_URL` and
`CONVEX_SELF_HOSTED_ADMIN_KEY` are set:

```bash
cd ../apps/web
set -a; source ../../self-hosted/.env; set +a
# If apps/web/.env.local exists (dev checkout), its CONVEX_DEPLOYMENT
# conflicts with self-hosted deploys — clear it for these commands:
export CONVEX_DEPLOYMENT=
npx convex env set AUTH_MODE "$AUTH_MODE"
npx convex env set NEXT_PUBLIC_APP_URL "$APP_URL"
# Convex Auth mode (a placeholder; no Clerk token ever arrives):
npx convex env set CLERK_JWT_ISSUER_DOMAIN "https://convex.invalid"
# Clerk mode instead:
# npx convex env set CLERK_JWT_ISSUER_DOMAIN "https://<your-clerk-issuer-domain>"
# Convex Auth without email:
# npx convex env set AUTH_EMAIL_VERIFICATION off
# Email through Resend (sign-up links in Convex Auth mode, invitations in both):
# npx convex env set RESEND_API_KEY "re_..."
# npx convex env set EMAIL_FROM "Convoy <noreply@yourdomain>"
# npx convex env set SUPPORT_EMAIL "help@yourdomain"
npx convex deploy
```

**4. Build and start the web app:**

```bash
cd ../../self-hosted
docker compose up -d --build web
```

Open `http://127.0.0.1:3000` and sign up (Convex Auth) or sign in through
Clerk. Your first workspace is created for you. The Convex dashboard is at `http://127.0.0.1:6791` (log in
with the admin key).

**5. Connect the CLI.** Nothing changes for CLI users — `convoy setup`
against `http://127.0.0.1:3000` works as usual. The CLI derives the HTTP
actions endpoint from the Convex URL: `*.convex.cloud` → `*.convex.site`
on managed Convex, port `:3210` → `:3211` on self-hosted. Keep that port
convention if you put a reverse proxy in front.

## Serving beyond localhost

The defaults assume one machine. To serve a team:

- Set `CONVEX_CLOUD_ORIGIN`, `CONVEX_SITE_ORIGIN`, and `APP_URL` in `.env`
  to URLs reachable from users' browsers and CLI machines (these origins
  are embedded in tokens and the web bundle — they must match exactly).
- Put TLS in front (Caddy/nginx/Traefik). Preserve the `:3210`/`:3211`
  pairing, e.g. `convex.example.com:3210` and `convex.example.com:3211`.
- Turn on email verification before opening sign-up to the internet. With it
  off, anyone who reaches the app can sign up under any address.
- Rebuild the web image after changing `.env`
  (`docker compose up -d --build web`) — the values are baked in at build.

## Operations

- **Upgrades**: `docker compose pull && docker compose up -d`, then re-run
  `npx convex deploy` after pulling a new Convoy version. Pin image tags
  instead of `latest` for reproducibility, and follow
  [convex-backend releases](https://github.com/get-convex/convex-backend/releases).
- **Backups**: data lives in the `convex_data` Docker volume (embedded
  SQLite + file storage). Snapshot the volume, or use
  `npx convex export` for a logical export. You own backups now — there is
  no managed restore.
- **Scaling**: the self-hosted image is a single-node build. Vertical
  scaling only; for real load you can move the database to Postgres/MySQL
  (`DATABASE_URL`) and file storage to S3, but the backend itself stays one
  process.
- **Optional backend flags**: `docker-compose.yml` ships with a few
  commented-out variables. The backend rejects *empty* values at boot, so
  each one must be uncommented in the compose file **and** given a value in
  `.env`: `DATABASE_URL` (external Postgres/MySQL instead of the embedded
  SQLite volume), `DO_NOT_REQUIRE_SSL=true` (when that database connection
  has no TLS — typical for a same-host Postgres), and
  `REDACT_LOGS_TO_CLIENT=true` (hide server error details from connected
  clients — recommended once real users are on the instance).

## What you lose versus managed Convex

Self-hosted Convex has feature parity with the cloud free tier for the
things Convoy uses — realtime queries, mutations, actions, HTTP actions,
scheduler/crons, file storage, full-text search, and components (Convoy
uses `migrations` and `resend`) all work. What you give up is the managed
layer around it:

| Capability | Managed Convex | Self-hosted |
|---|---|---|
| Realtime, scheduler, file storage, components | ✓ | ✓ |
| Scaling | Automatic, multi-service | Single node, vertical only |
| Backups / restore | Managed snapshots, point-in-time | Your volume snapshots + `npx convex export` |
| Log streaming (Axiom, Datadog, …) | ✓ | Not sent; use `docker logs` / dashboard |
| Preview & per-developer cloud deployments | ✓ | One deployment; run more compose stacks yourself |
| Dashboard access control | Team accounts | Single shared admin key |
| Availability, upgrades, on-call | Convex's problem | Your problem |

The recipe is intended to support the same Convoy features. Verify tasks,
realtime updates, attachments, invitations, MCP, and CLI registration on
your deployment before relying on it for team work.

## Validation status

The `self-hosted/` compose file follows the
[official Convex self-hosting guide](https://docs.convex.dev/self-hosting)
and Convoy's URL handling supports the self-hosted port convention, but
if you hit issues the most likely suspects are the ones any self-host
deployer should verify first: token validation from inside your
network (Clerk's issuer, or the backend's own JWKS in Convex Auth mode), file uploads, scheduled jobs (task hard-delete, stream
watchdogs), and CLI agent registration over `:3211`.
